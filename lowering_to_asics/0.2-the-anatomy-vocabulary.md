# 0.2 — The Anatomy Vocabulary: Six Questions Every Accelerator Must Answer

*Post 0.2 of **One Kernel, Many Chips**. Previous: [0.1 — One Stack, Many
ASICs](0.1-one-stack-many-asics.md). Next: 1.1 — The Systolic Contract: Inside
the Google TPU.*

---

Every accelerator talk invents its own nouns. Google says *MXU, VMEM, ICI*.
AWS says *NeuronCore, SBUF, PSUM, NeuronLink*. Groq says *TSP, lane, SRAM*.
Tenstorrent says *Tensix, NoC, RISC-V*. Cerebras says *PE, fabric, CSL*. It is
tempting to conclude these machines share nothing.

They share *six questions*. The nouns are brand names for the answers.

This post is the series' shared vocabulary: the six questions, the three memory
archetypes most chips collapse into, and the roofline scorecard that every
architecture post (1.1 onward) will fill in for its target. If 0.1 was the
toolchain, 0.2 is the measuring stick.

## 1. The six questions

![The anatomy vocabulary](../diagrams/accelerator-questions.svg)
*(source: [`diagrams/accelerator-questions.mmd`](../diagrams/accelerator-questions.mmd))*

### Q1 — Compute fabric: what *is* a "tile" here?

The taxonomies you'll meet, in increasing weirdness:

- **Systolic arrays** (TPU MXU, edge NPUs): a grid of MACs where a tile of A and
  a tile of B *flow through each other*; the "instruction" is mostly implicit.
  Great for GEMM-shaped work; everything else (softmax, norms, gathers) needs a
  different unit or a different schedule.
- **Engine arrays** (Trainium's vector/tensor/special engines, Gaudi's MME+TPCs):
  several *named* programmable engines with different talents; the compiler's job
  includes cast type-casting ops to engines.
- **RISC-V + accelerator tiles** (Tenstorrent Tensix): general-purpose cores with
  matrix/vector units bolted on and a network between them; "fabric" is literal —
  your kernel is partly a *network program*.
- **Streaming / static-functional units** (Groq TSP): dedicated units (matmul,
  vector, memory movers) that all run on a compiler-owned clock; a "tile" is a
  scheduled pipeline stage.
- **Fixed-function blocks** (Etched Sohu, edge NPUs, Apple ANE): the op set is
  *silicon*; lowering is scheduling and tiling of a baked-in graph.

TinyMoE's expert GEMM (kernel 1) sits comfortably on all of them. Kernel 5 — the
top-k gather — sits comfortably on none.

### Q2 — Memory hierarchy: who moves data, and when?

![Three memory archetypes](../diagrams/memory-archetypes.svg)

Almost every chip is one of three archetypes:

**A. HBM + compiler-managed scratchpad** (TPU's VMEM, Trainium's SBUF/PSUM).
The scratchpad is fast (tens of TB/s effective) but *small and manual*: the
lowering must explicitly stage tiles, usually double-buffer to hide HBM latency
(two-to-four times ~2–8 TB/s). This is where "the compiler" and "the memory map"
become the same subject.

**B. SRAM only** (Groq LPU: ~230 MB on-chip, ~80 TB/s aggregate). No HBM
cliff — and no place to hide. The model (or the working set at a given serving
batch) must fit; *every* byte movement is a scheduled event. Bandwidth is
extraordinary; capacity is the constraint.

**C. Distributed on-die SRAM** (Cerebras WSE: 44 GB spread over the wafer). No
single memory pool at all — data streams PE to PE. Lowering maps graph stages to
places and routes streams between them.

Why this is Q2 and not Q5: **memory decisions usually dominate compute
decisions.** A worked bit of arithmetic, using TinyMoE shapes (B=2, S=512, so
T=1024 tokens, D=256, bf16 = 2 bytes):

> **RMSNorm** (kernel 3) over `[T, D]`: reads `T·D·2 = 512 KiB`, writes `512 KiB`
> (fusion can save one of the two). FLOPs ≈ `5·T·D ≈ 1.3 MFLOP`. Arithmetic
> intensity ≈ **1 FLOP/byte**. At 4 TB/s of HBM that kernel takes ~0.26 ms and
> would need 4 PFLOP/s to be compute-bound — it never will be. It is a bandwidth
> creature, and on archetype A it *lives or dies by fusion into a neighbor*.

### Q3 — Scheduling model: who owns concurrency?

The spectrum, and its two poles:

- **Static, compiler-scheduled** (Groq is the extreme): the compiler assigns
  every operation to a time slot; hardware is a deterministic pipeline. Amazing
  latency, zero jitter — and every `if` in the model must be resolved at compile
  time or paid as predication.
- **Dynamic, hardware-scheduled** (GPUs; most engines to a degree): work queues,
  caches/scratchpads with hardware movement, threads that take data-dependent
  paths.

TinyMoE's **router is the stress test**. `top-k` routing is data-dependent: the
tokens each expert sees aren't known until runtime. A static machine must either
(a) schedule all E experts for every token and predicate off the unchosen ones,
(b) bucket tokens at runtime and re-enter the schedule, or (c) require the
serving stack to constrain routing (a real design option — see Part B posts).
A dynamic machine just... branches. The cost shows up differently, but it always
shows up. This one question will generate the best material in every Part B.

### Q4 — Interconnect: how far does the kernel scale?

On-chip: a NoC (Tenstorrent), a mesh of cores sharing scratchpads (TPU VMEM +
ICI within a board), or a wafer fabric (Cerebras). Off-chip: chip-to-chip links
(NeuronLink, ICI pods of 9,216 chips), often with collectives (all-reduce for
expert parallelism) implemented in hardware or in firmware.

For TinyMoE, Q4 is where **expert parallelism** lives: E experts want E places to
run, and the weighted combine wants a reduction. That's interconnect traffic
shaped exactly like the model's routing.

### Q5 — Numerics: what do the bytes *mean*?

The ladder of the moment: BF16/FP16 → FP8 (e4m3/e5m2) → FP4/FP6 with block
formats (MX). Two consequences for lowering:

1. **Bandwidth per operation shrinks**, which moves memory-bound kernels *up* the
   roofline — often FP8 is a memory optimization before it is a compute one.
2. **Tile geometry changes**: block-scaled formats make the *scale factors* part
   of the tile; the layout pass must place them where the hardware expects.

Series convention: TinyMoE runs BF16 with fp32 accumulation (the classic
"what the engines actually do" combo); each Part A records the target's format
support and each Part B notes where format conversion is inserted in the lowering.

### Q6 — Programming model: where can you *intervene*?

Two offerings per chip, usually:

- **Whole-graph compiler**: give it PyTorch/JAX/ONNX, get a binary (XLA on TPU,
  Neuron SDK on Trainium, tt-forge on Tenstorrent). Great baseline, opaque
  corners.
- **Kernel DSL**: drop beneath the graph for hand scheduling (Pallas/Mosaic on
  TPU, NKI on Trainium, TT-Metal/TT-Lang on Tenstorrent, CSL on Cerebras). This
  is where our Triton kernels port to, and where Part B posts do their hands-on
  work.

Q6 answers "if the graph compiler makes a bad choice on kernel 3, what is my
escape hatch?" — and how much of our `tile.*` middle survives the trip into the
DSL.

## 2. The roofline, and where TinyMoE lives on it

The roofline model is one plot and one sentence: *a kernel's speed is bounded by
either its arithmetic intensity (FLOP per byte moved) times the memory
bandwidth, or the peak compute — whichever is lower.*

![Roofline primer](../diagrams/roofline.svg)

Arithmetic intensity (AI) is a property of the kernel and shapes, not the chip.
For TinyMoE at B=2, S=512, D=256 (bf16, rounded numbers):

| Kernel | Character | AI ≈ FLOP/byte | Bound by | The ASIC question it asks |
|--------|-----------|----------------|----------|---------------------------|
| 4 `swiglu_fwd` | elementwise | ~0.3 | bandwidth | fuse me into the GEMM before I hurt you |
| 3 `rms_norm_fwd` | reduction + elementwise | ~1 | bandwidth | what's your fusion story? |
| 5 `moe_topk_gather` | irregular | <1 | bandwidth + latency | can your schedule represent data-dependence? |
| 2b softmax core | reduction | ~5 | bandwidth-ish | which unit runs exp/sum, at what rate? |
| 2a/2c `QKᵀ`/`PV` | tiled matmul | ~30–70 | approaching compute | how do I tile without materializing S×S? |
| 1 `expert_gemm` | grouped matmul | ~100+ | compute | show me your tensor engine mapping |

Read the table left to right and you have the plot: the elementwise and gather
kernels hug the bandwidth roof; the GEMMs sit at or under the compute roof; the
attention core sits *under both, depending on your tiling* — which is why
flash-style kernels (see `kernels_triton.py`) are the favorite demo of every
compiler team in the industry.

The roofs themselves (the two lines) are chip-specific: that's Part A material.
Post 1.1 will draw real numbers for TPU v7-class hardware on this same plot.

## 3. The scorecard

Every Part A post ends with this table filled in; every Part B post extends the
right column with lowering evidence. This is the series' bookkeeping — sixteen
posts, one comparable grid.

| Field | Filled in |
|---|---|
| **Q1 Compute fabric** | (systolic / engines / mesh / streaming / fixed) |
| **Q2 Memory archetype** | (A: HBM+scratchpad / B: SRAM-only / C: distributed) + numbers |
| **Q3 Scheduling** | static ↔ dynamic, and the router story |
| **Q4 Interconnect** | on-chip + scale-out, collectives |
| **Q5 Numerics** | formats, accumulation width, where conversions land |
| **Q6 Programming model** | graph compiler + kernel DSL names, escape hatches |
| **Roofline** | peak vs. bandwidth; where kernels 1–5 land |
| **The leak** | what the portable `tile.*` IR could *not* express — filled in Part B |

That last row is the most important. In 0.1 we lowered `tile.gemm` to generic
loops and the IR said nothing about hardware. Every architecture will force
something extra to be said — buffer spaces (`memref<..., 3>` on some targets),
layout attributes, synchronization ops, scheduling constraints. **The leak is the
difference between the portable promise and the performant program**, and
recording it per-target is how this series stays honest.

## 4. Where this meets the lowerer

In 0.1, `lower_tile_gemm` made exactly four kinds of decision: loop order, tile
sizes, where loads live, what fuses. The vocabulary now has names for them:

- tile sizes ← **Q1** (what fits the fabric) + **Q2** (what fits the scratchpad)
- load/store placement ← **Q2** (who moves data)
- fusion ← **Q2/Q5** (bandwidth, numerics of the epilogue)
- synchronization ← **Q3** (who owns concurrency) + **Q4** (cross-core)

When Part B posts extend `code/lowerer/`, they'll add a target hook per row of
the scorecard. The vocabulary isn't decoration — it's the crate's module layout
waiting to happen.
