# 0.1 — One Stack, Many ASICs

*This is post 0.1 of **One Kernel, Many Chips** — a series about lowering ML models
onto AI ASICs with Triton, MLIR, and Rust. Post 0.2 is
[The Anatomy Vocabulary](0.2-the-anatomy-vocabulary.md).*

---

Every AI accelerator company eventually shows you the same slide: a block diagram
of their chip, some boxes labeled "matrix engine" and "SRAM", and an arrow into a
box labeled "compiler". This series lives inside that last box.

**Lowering** is what compilers do when they take a description of *what* to compute
and produce a description of *how* a specific machine computes it. For AI ASICs,
that "how" is where the interesting disagreements are: a Google TPU wants your
matmul expressed as tiles poured through a systolic array; a Groq LPU wants your
entire layer unrolled into a static schedule of instruction slots; a Cerebras WSE
wants a graph of streams routed across a wafer. Same kernel, radically different
answers.

The claim this series will test: **you can watch every one of those disagreements
from a single portable middle layer, with one kernel inventory, one tool stack,
and one vocabulary.** Rust + [Melior](https://github.com/mlir-rs/melior) drive the
lowering; [Triton](https://github.com/triton-lang/triton) and PyTorch define what
computes; each architecture gets a two-part deep dive — anatomy first, lowering
second.

This post sets up the stack and the running example, then lowers our first kernel
all the way to loops and explicit memory traffic, in Rust.

---

## 1. The stack

![The series stack](../diagrams/series-stack.svg)
*(source: [`diagrams/series-stack.mmd`](../diagrams/series-stack.mmd))*

Three layers, three artifact types:

1. **What to compute** — `code/model/tiny_moe.py` (PyTorch model) and
   `code/model/kernels_triton.py` (Triton kernels). This layer is written once
   and never changes.
2. **The portable middle** — a tile-level IR. Tile-level means the program talks
   about *blocks of data* ("load a 64×64 tile of A, dot it with a 64×64 tile of B")
   and stays silent about hardware. Triton's `tt` dialect is the famous example;
   we'll build a tiny stand-in (`tile.*`) to see the mechanics from the inside.
3. **Target reality** — a target dialect and eventually an ISA per chip. This is
   what each Part B post in the series owns.

### Why Triton for layer 1–2?

Triton programs are already tile-level: `tl.dot(tl.load(...), tl.load(...))` is
exactly the granularity ASIC compute fabrics eat. That makes a Triton kernel a
near-perfect *specification* of what any given ASIC's compiler must reproduce.
(The production evidence for this is strong: Meta's [Triton for
MTIA](https://arxiv.org/html/2608.00325) work lowered GPU-authored Triton kernels
onto a custom accelerator; academic work like [TL](https://arxiv.org/pdf/2512.22168)
lowers Triton onto spatial dataflow machines.)

### Why Rust + Melior for layer 2–3?

- **Melior is MLIR's C API with Rust's type system on top.** You build and rewrite
  IR from a safe language, and run upstream MLIR passes (canonicalizer, CSE, …)
  without writing C++.
- **Compiler code is the code you revisit most.** Ownership, pattern matching over
  IR shapes, and fearless refactoring matter more here than in a research script —
  Rust is the rare language that makes a multi-target lowering pipeline feel like
  a program rather than a pile of Python string templates.
- **Prototyping dialects in pure Rust.** As we'll see below, MLIR lets us use
  unregistered ops while the IR is still settling — no TableGen tax until the
  design is right.

## 2. The running example: TinyMoE

We need one model whose *kernel inventory* is boring enough to follow for fourteen
posts and rich enough to stress every architecture differently. A dense
transformer is too polite: its whole life is GEMM. An SSM is great drama
(recurrence!) but its kernel set is narrow. So we run a tiny Mixture-of-Experts
language model — **TinyMoE** — frozen at these shapes for the whole series:

> D=256, 4 heads (Dh=64), 2 decoder blocks, 4 experts with top-2 routing,
> expert hidden 512, context 512, vocab 1024. ~4M parameters.

```python
# code/model/tiny_moe.py — the skeleton of the running example.
@dataclass(frozen=True)
class TinyMoEConfig:
    vocab_size: int = 1024     # toy vocab (keeps embedding small)
    d_model: int = 256         # model width D
    n_heads: int = 4           # head_dim = D / n_heads = 64
    n_layers: int = 2          # decoder blocks
    n_experts: int = 4         # experts per MoE layer (E)
    top_k: int = 2             # experts activated per token (k)
    expert_hidden: int = 512   # expert FFN width H_ff
    max_seq: int = 512         # context length S
```

Two design choices are load-bearing for the series:

**Attention is written out explicitly**, not delegated to
`F.scaled_dot_product_attention`, so the three phases we will lower — `QKᵀ`,
softmax, `PV` — stay visible:

```python
# Phase 1: scores = Q K^T / sqrt(Dh)   (matmul → tensor engines)
scores = (q @ k.transpose(-2, -1)) / (self.head_dim ** 0.5)
# Phase 2: softmax over rows            (reduction → vector engines)
attn = torch.softmax(scores, dim=-1)
# Phase 3: out = attn V                 (matmul again)
out = attn @ v
```

**Routing is data-dependent.** The MoE layer's `top-k` gather decides *which
compute happens on which data* at runtime — the piece that breaks static-schedule
machines and maps onto special hardware like TPU SparseCores:

```python
# Kernel 5: top-k routing. DATA-DEPENDENT control flow — the router
# decides the compute pattern after seeing the activations.
topk_w, topk_ix = torch.topk(probs, self.top_k, dim=-1)   # [T, k]
...
for e, expert in enumerate(self.experts):
    idx, slot = torch.where(topk_ix == e)   # a gather plan: irregular!
    if idx.numel() == 0:
        continue
    out.index_add_(0, idx, w * expert(x[idx]))
```

![TinyMoE and its kernels](../diagrams/tinymoe-kernels.svg)
*(source: [`diagrams/tinymoe-kernels.mmd`](../diagrams/tinymoe-kernels.mmd))*

The contract for the rest of the series is this inventory — five kernels, five
*characters*:

| # | Kernel | Character | What it probes on any ASIC |
|---|--------|-----------|----------------------------|
| 1 | `expert_gemm` | compute-bound | tiling, tensor-engine mapping, grouped GEMM |
| 2 | `attention_fwd` | fused + tiled | online softmax, buffer scopes, masking → loop bounds |
| 3 | `rms_norm_fwd` | memory-bound | fusion or pay the bandwidth bill |
| 4 | `swiglu_fwd` | memory-bound | epilogue fusion opportunities |
| 5 | `moe_topk_gather` | irregular | dynamic routing vs. static schedule |

Kernel 1 is already in Triton (`code/model/kernels_triton.py`), and it looks
exactly like you'd expect — a tile loop with `tl.dot` at its heart:

```python
# Triton: tiled GEMM, kernel 1 of the inventory.
@triton.jit
def matmul_kernel(a_ptr, b_ptr, c_ptr, M, N, K, ...,
                  BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr, BLOCK_K: tl.constexpr):
    ...
    acc = tl.zeros((BLOCK_M, BLOCK_N), dtype=tl.float32)
    for _ in range(0, K, BLOCK_K):
        a = tl.load(a_ptrs, mask=..., other=0.0)
        b = tl.load(b_ptrs, mask=..., other=0.0)
        acc += tl.dot(a, b)          # <-- tl.dot is the tensor-engine / MXU op
        ...
    tl.store(c_ptrs, acc.to(c_ptr.dtype.element_ty), mask=...)
```

> **Why the tile sizes are `constexpr` here matters.** Triton bakes the hardware
> tile into the schedule at compile time. Every ASIC discussion in this series is,
> at bottom, a discussion about what those tile sizes should be, where the tiles
> live, and who moves them.

## 3. The first lowering: `tile.gemm` → loops, in Rust

Here is the whole thesis of the series in one screen. We take kernel 1's shape
(expert GEMM: `C += A @ B`), express it at the tile level, and lower it to
explicit loops and memory traffic — **with Rust code driving MLIR through Melior**.

### 3.1 The portable middle: a `tile.*` dialect

MLIR dialects are normally defined in C++ with TableGen — verifiers, custom
syntax, the works. But for a settling IR design, MLIR allows *unregistered* ops:
structurally valid operations with no dialect definition. That's our prototyping
lane, and it keeps this post's code 100% Rust:

```rust
// code/lowerer/src/main.rs
// `tile.gemm` is an unregistered op standing in for Triton's tile dialect.
// Dims ride along as attributes so the printed IR is self-describing.
let gemm = OperationBuilder::new("tile.gemm", location)
    .add_operands(&[a, b, c])
    .add_attributes(&[
        (Identifier::new(context, "m"), IntegerAttribute::new(spec.m, index_type).into()),
        (Identifier::new(context, "n"), IntegerAttribute::new(spec.n, index_type).into()),
        (Identifier::new(context, "k"), IntegerAttribute::new(spec.k, index_type).into()),
    ])
    .build()?;
```

`cargo run` prints the before-state:

```mlir
// ---- before: tile-level IR (portable middle) ----
module {
  func.func @expert_gemm(%arg0: memref<16x16xf32>,
                         %arg1: memref<16x16xf32>,
                         %arg2: memref<16x16xf32>) {
    "tile.gemm"(%arg0, %arg1, %arg2) {k = 16 : index, m = 16 : index, n = 16 : index}
      : (memref<16x16xf32>, memref<16x16xf32>, memref<16x16xf32>) -> ()
    return
  }
}
```

One op. No loops, no buffers, no hardware. *What* to compute, nothing about *how*.

### 3.2 The rewrite

`lower_tile_gemm` expands that one op into a loop nest with explicit
`memref.load`/`memref.store`. This is exactly the decision point each ASIC vendor
re-implements — loop order and tile sizes (what fits the scratchpad), where the
loads live (who moves data), what fuses into the loop (epilogues):

![The lowering pass](../diagrams/lowering-pass.svg)
*(source: [`diagrams/lowering-pass.mmd`](../diagrams/lowering-pass.mmd))*

The region-nesting pattern in Rust is worth staring at, because it's how you
build any structured op (loops, ifs) through Melior: build the body block first,
then move it into the region:

```rust
// code/lowerer/src/main.rs — the heart of lower_tile_gemm.
// scf.for's region contract (verifier-enforced): exactly one block, one `index`
// block argument (the induction variable), terminated by `scf.yield`.
let i_body = {
    let i_block = Block::new(&[(index_type, location)]);
    let i: Value = i_block.argument(0)?.into();

    let j_body = {
        let j_block = Block::new(&[(index_type, location)]);
        let j: Value = j_block.argument(0)?.into();

        let k_body = {
            let k_block = Block::new(&[(index_type, location)]);
            let k: Value = k_block.argument(0)?.into();

            // %0 = memref.load %a[%i, %k] ; %1 = memref.load %b[%k, %j]
            let a_ik: Value = k_block.append_operation(
                OperationBuilder::new("memref.load", location)
                    .add_operands(&[a, i, k])
                    .add_results(&[f32_type])
                    .build()?)?.result(0).unwrap().into();
            let b_kj: Value = /* same shape of code for %b[%k, %j] */;

            // %2 = arith.mulf %0, %1  — one FMA step of the GEMM
            let prod: Value = k_block.append_operation(
                OperationBuilder::new("arith.mulf", location)
                    .add_operands(&[a_ik, b_kj])
                    .add_results(&[f32_type])
                    .build()?)?.result(0).unwrap().into();

            // %4 = arith.addf %3, %2 ; memref.store %4, %c[%i, %j]
            ...
            // Every scf.for body ends in scf.yield (no iter_args here).
            k_block.append_operation(OperationBuilder::new("scf.yield", location).build()?)?;
            let region = Region::new();
            region.append_block(k_block);
            region
        };
        // wrap into the j-loop, etc. — see the source for the full nest
        ...
    };
    ...
};
```

And the after-state, plus one of the nicer perks of parking your IR in MLIR:
upstream passes run from Rust, no C++ involved:

```rust
// Phase 3 — run *upstream MLIR passes* from Rust.
let pass_manager = PassManager::new(&context);
pass_manager.add_pass(transform::create_canonicalizer_pass());
pass_manager.add_pass(transform::create_cse_pass());
pass_manager.run(&mut after)?;
```

```mlir
// ---- after: lower_tile_gemm + canonicalize + cse ----
func.func @expert_gemm(%arg0: memref<16x16xf32>, %arg1: memref<16x16xf32>,
                       %arg2: memref<16x16xf32>) {
  %c0 = arith.constant 0 : index
  %c1 = arith.constant 1 : index
  %c16 = arith.constant 16 : index
  scf.for %i = %c0 to %c16 step %c1 {
    scf.for %j = %c0 to %c16 step %c1 {
      scf.for %k = %c0 to %c16 step %c1 {
        %0 = memref.load %arg0[%i, %k] : memref<16x16xf32>
        %1 = memref.load %arg1[%k, %j] : memref<16x16xf32>
        %2 = arith.mulf %0, %1 : f32
        %3 = memref.load %arg2[%i, %j] : memref<16x16xf32>
        %4 = arith.addf %3, %2 : f32
        memref.store %4, %arg2[%i, %j] : memref<16x16xf32>
      }
    }
  }
  return
}
```

Same kernel, two IRs: one is a promise, the other is a plan. **Every architecture
post in this series is about what happens in between.** On the TPU, those three
loops get tiled to scratchpad shapes and the loads become DMAs into VMEM. On the
Groq LPU, the nest gets fully unrolled into static instruction slots and the
loads *are* the schedule. On Tenstorrent, the nest becomes RISC-V firmware on a
Tensix core next to a NoC router. The loops you just saw are the last common
denominator.

A small honest note about the companion code: production compilers discover ops
by walking the IR and extract `m`/`n`/`k` from attributes or static memref
shapes. Melior supports both; to keep this file focused on *emission*, both
builders read a `GemmSpec` struct that mirrors the tile op's fields. The IR
before/after is exactly what the rewrite produces.

## 4. Why C++/CUDA (still) enters here

The promise is "lowering logic in Rust", not "no C++ anywhere in the industry".
In the interest of honesty — and because every later post will hit the same
walls — here is where and why C++/CUDA re-enters:

| Boundary | Why it can't be Rust (or can't be *just* Rust) |
|---|---|
| **Executing Triton kernels** | Triton's mature backends emit GPU machine code (NVPTX → CUDA, AMDGCN). Running kernel 1–5 needs a GPU. On CPU-only machines we run the PyTorch paths — they are the reference numerics every lowering is checked against. (Triton-CPU exists but is experimental.) |
| **Production dialects** | Real portable IRs (`tt`, `ttir`, Neuron tile ops) are *registered* C++/TableGen dialects: verifiers, custom assembly syntax, canonicalization patterns. Our `tile.*` is unregistered on purpose — great for prototyping, but generic syntax and no verification beyond structure. |
| **Vendor toolchains** | XLA/PJRT, `neuronx-cc`, `tt-mlir` are C++ compilers invoked as subprocesses. The series *inspects and drives* them (including their IR); rewriting them in Rust is nobody's side quest. |
| **Reference numerics** | Checking a lowering against cuBLAS (via `cudarc`) when a GPU is present is the cheapest ground truth. Pure-Rust BLAS (`faer`) works too — but when GPU results are the target, GPU BLAS is the referee. |

Everything in `code/lowerer/` is pure Rust against MLIR's C API; the C++ world is
behind subprocess and FFI boundaries, exactly where it belongs.

## 5. Running the code

```sh
# the model + kernel definitions (CPU smoke test; kernels need a GPU to run)
python3 code/model/tiny_moe.py

# the lowering (needs LLVM/MLIR 23 — see code/lowerer/README.md)
cd code/lowerer && cargo run
```

Expected: a TinyMoE forward pass with shape/loss printout and the five-kernel
inventory, then three IR dumps (tile-level, lowered, post-pass).
